# Развитие секвенсора MIDI и двух режимов Song Mode в Am MOD

Основной вывод: штатный секвенсор уже хранит редактируемые нотные события с velocity, длительностью и Tune/Chop. Следует сохранить его запись, музыкальные часы, обработку повторов и нативную историю. Первый недостающий мост — между клавиатурой Synth и этим трактом. Horizontal Arrangement следует строить как модель музыкальных партий и блоков с компиляцией в один поток событий для существующего движка.

Основа анализа — `AlekseyMalykh/am-mod`, `main`, commit `a99d4745f3f99139bb5428279b3e3cd7456ec8bf`, полученный 23 ноября 2026 года, опубликованная линия r30d-beta3. Это существенно новее текущего checkout `codex/pad-phone-input` (`98d5b98`). Исследован отдельный снимок исходников; незакоммиченные изменения обоих локальных checkout не использовались как опубликованная основа и не менялись.

Ниже «существует» означает наличие реализации в этом commit. Это не означает подтверждения функции на физическом MPC. Разделы о новой архитектуре и этапах описывают предложение, а не готовую функцию.

## Что уже реализовано

### Музыкальные события и запись

`src/step_native.h` объявляет 56-байтовый `step_event`: время `int64_t`, тип/флаги и 40 байт данных. Поддержанный модом нотный вариант имеет tag 3 и inline payload. Другие варианты нельзя безусловно копировать: у tag 4 есть владение объектом через счётчик ссылок.

В исследованном ABI нотное событие содержит:

| Поле | Расположение | Значение |
|---|---|---|
| Start | `event.time` | Музыкальная позиция |
| Velocity | `event.data + 0` | `float`, нормированная величина |
| Choices | `event.data + 4` | Маска и упакованные параметры, включая Tune и Slice |
| Duration | `event.data + 24` | `int64_t` |
| Sound note | `event.data[32]` | Нативная нота источника, не обязательно абсолютная высота мелодии |
| Probability | `event.data[34]` | Вероятность |
| Repeats | `event.data[36]` | Упакованное количество повторов |
| Channel | `(event.type >> 12) & 15` | Канал, отдельно от Sound и аудиовыхода |

Это карта ABI конкретной прошивки 1.3.0.12, а не новый формат хранения. `midi_event.c` уже предоставляет проверенное декодирование значений; повторять ручную интерпретацию choices не нужно.

Последовательности находятся в нативном Project; `batch_events.cc` использует получение sequence через `0x2909be0` и списка событий для нативного track через `0x2957ae0`. Список содержит дерево событий: header `list + 0x60`, sentinel `+0x68`, событие в узле `+0x20`. Program содержит взаимные таблицы pad → note (`+0x12a8`) и note → pad (`+0x14a8`). Pad A03 нельзя автоматически считать MIDI note 2.

Обычная секвенция записывает команды запуска инструментов, а не сумму их аудио. Отдельная запись Input/Resample может создавать аудиосэмпл и его запуск; получить исходные MIDI-ноты из уже записанной волны этой архитектурой нельзя.

`poly_record.c` уже направляет полифонические Tune/Chop и Chords в штатный Engine через `0x211b090`. Recorder владеет временем, длительностью, quantization и историей. Код различает одновременные ноты одного Sound по modifier choices и завершает нужную ноту через `poly_record_release_event`. Маркеры завершения существуют только в очереди recorder и не записываются в XPJ.

Важная аппаратная деталь уже обработана: физическое отпускание пэда приходит через отдельный virtual release slot, а не обязательно через velocity callback с нулём. Для нового ввода необходимо сохранить эту пару путей.

### Tune и Piano Roll

`music_settings.c`, `music_ui.c`, `poly_record.c` и `chords.c` уже составляют систему раскладок, транспонирования и аккордов. Synth использует `music_layout_pad_pitch` и те же музыкальные настройки для Mono/Piano/Scale/Degrees.

Существующий Piano Roll — `piano_roll.c/.h` с адаптером `piano_roll_native.inc` внутри `step_native.c`. Он читает те же нативные события, которые используют Events/Steps. Уже есть:

- Pad, Tune и Chop layers;
- добавление/удаление, изменение времени, высоты, длительности и velocity;
- множественное и прямоугольное выделение, Copy/Cut/Paste;
- quantize начала, конца или обоих; изменение высоты выделения;
- preview, проверка revision и применение через одну нативную Undo-команду;
- ввод с пэдов через `workflow_piano_input` → `batch_piano_input` → нативный worker/recorder;
- MIDI file import/export и лимит `PR_MAX_EVENTS = 8192` для представления.

Редактирование во время записи сейчас запрещает `roll_commit`. Новый режим должен сохранить это ограничение до появления проверенного способа объединять запись с редактированием. Лимит Piano Roll нельзя выдавать за установленный лимит всего движка.

### MIDI и встроенный Synth

`midi_tools.c` реализует Input Maps, независимые Pad/Levels Output Maps, Learn, Monitor и режимы Drum/Selected/Channels/Instrument. `midi_alsa.c` перехватывает существующих владельцев ALSA, исключая Control Surface по идентичности; второй конкурирующий MIDI reader не нужен.

Для Tune/Chop внешние клавиши могут проходить через нативный Engine (`midi_native.c::emu_play`). Но Synth Input mode и назначение канала Synth вызывают `am_synth_key` непосредственно и поглощают сообщение до штатного ввода. Поэтому наличие поддержки внешней MIDI-клавиатуры не означает запись её Synth-партии в секвенцию.

Выходной MIDI уже содержит полезный механизм владения нотами: `midi_context.c`, `midi_live.inc`, `midi_wire.c`, `midi_voice.c`. Он переносит происхождение события, использует occurrence ID и запоминает получателя Note Off. `AM_MIDI_VOICES = 256` относится к этому слою; это не полифония встроенного Synth. Probability и ratchets должны использовать решение штатного scheduler, без повторного расчёта.

Synth пока является отдельным программным инструментом:

- `synth.c` — восемь голосов, очередь на 64 команды, генерация при 44100 Hz;
- `mixer_control.c::mixer_control_pad` вызывает `am_synth_note(note, 100, 1)`;
- `phone_native.c` на Sample Record вызывает `am_synth_pad(pad, down)`;
- `am_synth_pad` также использует velocity 100; API не принимает velocity;
- эти пути не вызывают штатный recorder;
- `rear_native.cc` добавляет Synth в Input, проводит через Input FX и при нужных условиях добавляет результат в выход мониторинга;
- параметры Synth сохраняются глобально в `.am-mod-synth` через `music_settings.c`; отдельного полноценного project preset в исследованном archive bridge нет.

Есть две технические причины не подключать просто ещё один callback к `am_synth_note`. Очередь объявлена SPSC, хотя потенциальные источники — UI, MIDI и будущий scheduler; необходим аудит фактических потоков и единый producer. Переполнение `push` сейчас молча отбрасывает команду, в том числе Off. Кроме того, `stop(note)` завершает все голоса этой высоты, что недостаточно для независимого владения одинаковыми нотами двух партий.

### Sequential Song Mode

`song_ui.c` расширяет штатный SongScreen. Song хранит диапазон шагов по `+0x30/+0x38`, каждый шаг — два `int`: sequence и repeats. Повторы ограничены 99; проверка общей длины использует штатный предел `0x3137` тактов.

Insert/Delete/Clear/SetRepeats выполняются нативными Undo-командами. Мод добавляет duplicate/replace/move и интерфейс экспорта. Mixdown и Sequence — штатные операции; Stems и MIDI добавлены модом. Этот режим следует оставить самостоятельным и полностью работоспособным.

### Микшер и экспорт

В `mixer_model.h` аудионазначение — `mixer_project.output[128]`: 0 Master Direct, 1–8 A–H. Отдельны send destinations, FX, mute/solo и mixer scenes. `mixer_route_native.c`, `mixer_live_native.c`, `mixer_buses.c` перехватывают рендер инструментов и суммируют их в существующем тракте. Scene `part_id` предусмотрен моделью; комментарий о будущем Song adapter нельзя считать готовым связыванием с частями песни.

`mixer_stems.c` использует штатную offline timeline и отдельный экземпляр Mixer; пишет девять источников A–H и Master Direct наряду с Mixdown. Музыкальная дорожка не равна одному такому stem. Две партии, направленные на A, уже объединены в bus stem A; получить их раздельно из этого WAV нельзя.

Synth вызывается в обработчике Input. Его наличие в live monitoring не доказывает работу в offline export. Для MIDI Synth требуется отдельный render adapter, который обслужит Synth ровно один раз на блок и проведёт его через нужный mixer path и в live, и в offline.

### Save и Load

Уже используется совместимое расширение архива проекта:

- `music_archive.c`: музыкальные настройки, `amModMidiMapV1`, local sequence mutes и другие необязательные поля;
- `mixer_archive.cc`: отдельное поле `amMixerV1`, транзакционный capture/publish, revision и source generation;
- mixer archive сохраняет неизвестный/повреждённый payload как opaque bytes и запрещает редактировать его как известную модель;
- отсутствие расширения Mixer даёт legacy state и не заставляет добавлять поле при следующем сохранении.

Именно mixer archive — подходящий образец нового хранилища. Более простой fallback «не понял — восстановил defaults» из некоторых music extensions для аранжировки с пользовательскими нотами неприемлем.

## Предлагаемая модель данных

Sequence Track — логическая музыкальная партия. Native track pointer, MIDI channel, input device и Mixer bus являются отдельными сущностями. Во внутренней модели не использовать `track` без уточнения, какой именно смысл имеется в виду.

| Сущность | Предлагаемые поля и обязанности |
|---|---|
| MusicalTrack | `id`, name, colour, default instrument binding, mute/solo; необязательное правило первоначального выделения |
| InstrumentBinding | `id`, kind `NativePad / ChromaticSample / BuiltinSynth / ExternalMidi`, program/sound reference или synth instance/preset, port/channel для MIDI |
| Pattern | `id`, revision, name, `length_ticks`, event set, source provenance, optional parent variation ID |
| Note | `id`, start/duration ticks, absolute MIDI pitch 0–127, velocity, binding reference, optional input provenance |
| NativePadEvent | `id`, start/duration, sound identity и проверенные native modifier values, probability/repeats/mute; сохранение остальных поддержанных свойств |
| Clip | `id`, track ID, pattern ID, start tick, source offset, play length, repeat policy, transpose, gain/velocity adjustment, binding override |
| Arrangement | `id`, tracks, clips, end tick, global tempo/signature map, revision |
| SourceSnapshot | source sequence/program identity, event IDs, revision/fingerprint и снимок событий для безопасного восстановления |

Это логическая схема, не C struct для записи через `fwrite`. Время — `int64_t`, единица 960 ticks на четверть, как у существующего движка. Такт вычисляется из размера: для 3/4 это 2880 ticks, а не всегда 3840. Функции работы с размером есть в `midi_file_native.c::signature_events`; ограничения текущих 4/4 UI-подписей необходимо устранить в новом экране.

Для существующей Sequence источником истины остаётся нативный event list. Для извлечённого самостоятельного Pattern — его собственный набор событий. Одна и та же партия не должна иметь два независимо редактируемых источника истины.

Сразу после Split создаётся неизменяемый общий snapshot исходной Sequence и views с явным membership событий. Это дешёвое виртуальное разделение. Extract Pattern материализует выбранный диапазон с началом в нуле; дальнейшее редактирование оригинальной Sequence его не изменяет. Variation получает отдельный ID и независимую редактируемую ревизию. Допустимо разделять immutable event pages в RAM до первого изменения, но сохранённая variation должна восстанавливаться без доступности изменённого оригинала.

Clip repeat ссылается на один Pattern. События не дублируются в сохранённой модели при каждом повторе. Временная компиляция для проигрывания может разворачивать повторы; это кэш, который можно удалить и восстановить.

Absolute MIDI pitch нужен для смены инструмента. При выводе в ChromaticSample вычисляется Tune относительно Original Note; недоступный диапазон отклоняется с понятным сообщением. Chop сохраняет смысл slice trigger и не превращается автоматически в мелодическую ноту. Смена input layout после записи не должна транспонировать уже записанный материал.

### Split и неоднозначные события

Split by Pads группирует по program/sound/bank. Split by Mixer использует снимок назначения `output[pad]` в момент операции, включая Master Direct. Последующая перенастройка bus не переносит события между партиями. Split by Instrument/Channel работает только с реально имеющимися сведениями: исходный input port и способ ввода старые tag-3 события полностью не описывают.

Manual Split использует существующее выделение Piano Roll и назначает конкретные event IDs, а не все события данного pad. Если один pad играл бас и мелодию, автоматического безошибочного разделения нет; пользователь уточняет диапазон, высоту или выделение. Одинаковые по байтам одновременные события различаются occurrence ordinal внутри snapshot. Указатель на native tree node и изменяемый sequence index нельзя сохранять как стабильный ID.

По умолчанию событие принадлежит одной партии в рамках Split. «Копировать в другую партию» — отдельная операция с новым ID, иначе запуск обеих партий удвоит звук. Исходная Sequence не меняется; воспроизведение Arrangement не должно одновременно запускать её полный исходный поток.

При изменении источника живые views помечаются устаревшими. Не пытаться молча перепривязать неоднозначные события по высоте/времени. Предложить обновление снимка или оставить сохранённый материал.

## Два режима Song Mode

Sequential сохраняет штатный Song и его операции. Horizontal хранит Arrangement отдельно. Выбор режима — состояние представления/проигрывания, а не конвертация данных одного вида в другой. Режим по умолчанию для старого проекта — Sequential.

Переход между режимами во время Stop безопасен по умолчанию. Будущее переключение на границе такта должно использовать один transport command с отпусканием принадлежащих старому playback scope нот. Переход не должен менять выбранную штатную Sequence или удалять её события.

Convert Sequential to Arrangement — отдельная недеструктивная команда: раскладывает шаги по времени, учитывает repeats, длины и tempo policy; оригинальный Song остаётся. Обратная операция — Render to New Sequence/Sequences с предварительной проверкой штатных пределов. Это явный результат, появляющийся у пользователя в списке секвенций.

Для первой версии Horizontal — один общий темп и размер, задаваемые Arrangement/Project. Pattern не навязывает собственный BPM каждой параллельной дорожке. Sequence tempo и master tempo policy в Sequential сохраняются. Конвертация песни со сменами размера/темпа либо переносит их в map, либо явно сообщает о неподдержанной конвертации; молчаливое приведение к одному темпу недопустимо.

## Запись MIDI с физических пэдов

### Один дубль на нескольких музыкальных дорожках

Целевой workflow Horizontal Arrangement: при включённом распределении по назначенным музыкальным дорожкам один дубль может создать несколько параллельных clips. Каждый clip появляется только у дорожки, получившей принятые события; на пустых дорожках блоки автоматически не создаются. Начало take общее, события сохраняют абсолютную синхронизацию, а их локальные позиции считаются относительно размещения clip. В Auto length по умолчанию применяется общий округлённый конец дубля, чтобы партии сразу повторялись синхронно; затем длины можно независимо обрезать или расширить.

Пэд ударных/вокального sample записывает событие запуска соответствующего инструмента, Synth в нотном режиме — музыкальную высоту и длительность. Mixer A–H не определяет музыкальную дорожку автоматически. Если один пэд участвует в нескольких партиях, принимающая дорожка задаётся явным record target/правилом ввода; одно нажатие не размножается скрыто по всем дорожкам. Record arm и выбранное распределение должны быть видны до Play. Mute/solo не подменяет record arm.

Остаётся привычный вариант: весь дубль записывается в одну native секвенцию, а Split by Pads / Mixer / Manual создаёт независимые представления позднее. Вход в созданный clip открывает существующий Piano Roll/Events/Step для его Pattern. Создание take, clips и распределение событий должны отменяться согласованно. Это спецификация будущего Arrange; текущий Pad-to-MIDI trial сохраняет ноты на одном пустом carrier A16 и не создаёт эти дорожки/clips.

### Место записи и определение длины

Это два независимых выбора: работать из Arrange либо внутри открытого Pattern; писать новый дубль с Auto length, в фиксированный Loop или в Punch range. Внутри Pattern доступны живая запись с пэдов/MIDI, ручной Insert в Piano Roll/Steps и Copy/Paste. Все способы меняют один event set и используют существующую историю, а не создают отдельную аудиоверсию мелодии. Ручные структурные правки во время активной записи сначала остаются заблокированы, как в действующем редакторе; после Stop они доступны в том же материале.

New Take / Auto length не требует заранее созданного блока. Пользователь выбирает музыкальную партию, instrument binding и старт; Rec вооружает запись, Play начинает общий transport. На первом принятом событии создаётся take; в Arrange её размещение растёт, а внутри нового Pattern растёт длина. Stop завершает take. Граница по умолчанию округляется вверх до такта, реальные onset/duration сохраняются; оставшиеся held notes завершаются штатным recorder. Count-in и quantization наследуются от транспорта. Пустая take не создаёт лишних Pattern/clip, если пользователь явно не выбрал сохранить пустой материал.

Loop пишет в существующую/явно заданную длину и поддерживает native Rec/Overdub. Для shared Pattern до записи нужно выбрать исходник либо Make Variation; выбранный вариант виден на экране до Play. Punch пишет только внутри выбранного диапазона и имеет явный Add/Replace policy; материал вне диапазона не меняется. Ноты, пересекающие punch/loop границы, завершаются по проверенной native duration policy, а не по времени UI-перерисовки.

Растущая Auto take не перезаписывает соседний clip. В первой версии граница ближайшего clip на этой партии является пределом записи с показанным punch-out; для более длинного дубля пользователь заранее выбирает свободный диапазон/новую партию. Автоматический сдвиг соседних blocks или запись поверх них не включаются скрыто. Расширение take, создание Pattern/clip и запись событий должны отменяться согласованно.

Минимальное направление — общий musical input adapter поверх существующих Engine/recorder entrypoints и существующего пути Piano input. Раскладка только вычисляет pitch. Записываются pitch, реальная velocity, начало и длительность; источник ввода остаётся метаданными.

Предлагаемый поток:

```text
Physical pad down/up + velocity
  → captured layout pitch + input occurrence ID + project generation
  → existing music worker
  → native Engine and recorder
  → editable native note representation
  → common instrument dispatcher
  → Synth / chromatic sample / external MIDI
```

Нужны два адаптера представления: Native Pad events без изменения и MIDI notes через instrument binding. Ни канал 16, ни факт открытого Synth screen не могут служить постоянным признаком Synth-партии. Проигрывание и экспорт должны работать при закрытом Mixer.

Для самого первого runtime-прототипа допустим только явно выбранный пустой carrier Sound, представляющий Synth binding в текущем проекте. Native tag-3 + Tune хранит pitch относительно фиксированной базы, например 60; диапазон MIDI 0–127 укладывается в поддержанный Tune. Carrier здесь технический адрес адаптера, не аудиошина и не обязательная заранее созданная дорожка для обычной записи.

Такой прототип имеет строгие условия:

1. Не занимать pad автоматически, не менять сэмплы/Pad Link и не менять native event ABI. До первой записи проверить адресацию пустого carrier и возврат к исходному выбранному Sound.
2. На native note dispatch перехватывать только события binding текущего project generation. Не подавлять чужую Sequence, preview или обычный Sample input. Живое звучание должно идти через этот же dispatch, без второго прямого `am_synth_note`.
3. Note Off обязан пройти и в recorder, и в Synth независимо от наличия native sample voice. Текущий `midi_live.inc` может забыть событие без выходных MIDI routes; это нельзя считать готовым Synth voice registry.
4. Для session-only прототипа binding и тестовые события находятся только в отдельном тестовом контексте; Save реального проекта не должен утечь с экспериментальной адресацией. Если изоляция нативного контекста не подтверждена, сначала fixture/VM, без подключения к обычному приложению.
5. Перед сохранением пользовательских Synth-партий нужен известный versioned binding в расширении проекта и project preset Synth. Одна глобальная настройка `.am-mod-synth` не обеспечивает воспроизводимость проекта.

Carrier — ограничение первого вертикального прототипа. Canonical Pattern Note хранит абсолютный pitch и InstrumentBinding, поэтому замена Synth на sample или external MIDI впоследствии не зависит от carrier. Если доказанный native adapter позволяет отдельный нативный instrument context без carrier, использовать его; наличия безопасной фабрики такого контекста исследованный код пока не подтверждает.

На Down фиксируются pitch, binding, source key, velocity, generation и occurrence ID. На Up используются именно сохранённые значения, даже если пользователь изменил octave/layout/channel/selection. Stop, New/Load, выход из Keys, отключение MIDI и повторный Down закрывают прежнее владение предсказуемо. Для retrigger одной высоты нужны distinct occurrences; возможная MIDI gate policy не должна завершать чужую удерживаемую ноту.

Quantization/overdub первоначально наследуются от native recorder. Длительность не вычисляется по UI timer. Note Repeat нужно снимать после штатного repeat scheduler: записывать реально сгенерированные повторные ноты с gate, а не физическое удержание и второй набор повторов поверх него. Chords передают несколько pitch occurrences через тот же adapter. MIDI input Synth mode затем переводится на него, чтобы внешние клавиши и пэды записывались одинаково.

## MPC программы и MIDI файлы

Program — набор инструментов и настроек пэдов, MIDI file — музыкальные события, Pattern — редактируемая партия, Clip — её размещение в песне. PGM сам по себе не заменяет секвенцию и обычно требует сопровождающие samples. Загрузка MIDI не должна автоматически перезаписывать kit.

В основе `a99d474` уже есть `program_import.cc`, `program_pgm.c`, `program_manifest.cc`, `program_import_ui.inc`: PGM MPC1000 PGM1.00 и XML Drum XPM, предварительная проверка sample dependencies, выбор начального банка и запрет перезаписи занятых destinations, нативный commit с Undo. XPM manifest допускает Drum и четыре уникальных layers на pad. Это не универсальная совместимость со всеми MPC PGM, Keygroup, plugin programs, MPC projects и их FX. Импортируемые параметры нужно проверять по capabilities reader/engine и показывать отчёт supported/converted/unsupported; расширение `.pgm` не определяет его поколение.

Также уже есть SMF 0/1 с PPQN, MIDI file import в native Sequence через Pad Map/Tune/Chop и export Sequence/Song. В текущем UI выбирается track/channel, но нет полноценной таблицы назначения каждого исходного ряда на независимую партию/инструмент. Import сейчас добавляет notes; остальные channel messages подсчитываются в `controllers`, но не превращаются в automation lanes. SMPTE division, SMF2 и SysEx следует явно помечать неподдержанными/непереносимыми, а не обещать полный round-trip всех данных.

Предлагаемый единый workflow:

1. Browser → Programs → выбрать PGM/XPM → проверить samples и совместимость → выбрать свободный начальный банк → прослушать/импортировать как одну Undo-операцию. Занятые пэды видны до commit. Новый ремап может предлагать свободные отдельные destinations, но действующее ограничение «не перезаписывать» сохраняется. Program slots и быстрый swap нескольких kits — отдельная будущая функция, не предположение о готовой поддержке нескольких native programs.
2. Browser → MIDI → выбрать `.mid` → Review. Пользователь выбирает разбиение Track, Channel или Note rows. SMF0 обычно содержит один track с несколькими каналами; SMF1 может содержать несколько каналов в одном track. Программа не угадывает инструменты по номеру track. Для drums режим Note rows показывает отдельные высоты, например C1 Kick и D1 Snare, и назначает их разным sound pads.
3. В таблице назначений строка source track/channel/note получает Destination kind и конкретное назначение: Drum Kit → набор пэдов загруженной программы; Chromatic Sample → один sound pad с Original Note и сохранением мелодических интервалов; Synth → instrument binding; External MIDI → port/channel. Мелодический track не раскладывается автоматически по одному sample на каждую ноту. Одновременный remap нескольких source rows на один destination допустим только явно, с preview результата.
4. Timing по умолчанию Original: пересчёт PPQN в 960 без растяжения и quantize. Выбор Project tempo или Import tempo map явный; изменение BPM не равняется масштабированию MIDI ticks. Fit to Length — отдельная опция с preview. Review показывает imported/filtered/unmapped/out-of-range notes, CC, sustain, tempo и конец материала; никакого молчаливого обрезания до длины текущей Sequence. Для нового Pattern длина берётся из материала с округлением до музыкальной границы и сохранением нотных tails. Для текущей Sequence предлагаются Extend либо явный диапазон.
5. Import as Patterns создаёт независимые партии и может разместить их в Arrangement с общего такта; Import into Current Sequence добавляет в прежний workflow. Вся операция проверяется до commit и отменяется целиком. Исходный файл остаётся нетронутым.
6. Song → выбрать clip/sequence → Edit → Notes/Auto → Back. Split/Move/Repeat/Make Variation используют уже описанную модель. MIDI export доступен для выбранного Pattern, выбранных партий или полной Sequential/Horizontal Song; Mixdown/Stems остаются отдельными audio операциями.

Нужно различать два смысла назначения «строки на пэд». Sound pad определяет звучание ноты/инструмента. Clip pad выбирает или запускает целый Pattern в отдельном явно включённом режиме Parts/Clips. Один физический pad может выполнять обе роли в разных режимах, но обычная игра не должна внезапно запускать целую партию. В первом Horizontal workflow пэды выбирают партии/блоки; опциональный Launch mode с quantized start является отдельным расширением и не запускается автоматически после импорта.

MIDI channel сохраняется как исходное музыкальное свойство отдельно от pad index, затем instrument binding задаёт выходной channel/port. Program change из MIDI не означает загрузку PGM по номеру: без таблицы пользовательских назначений он сохраняется как метаданные/поддержанный message либо остаётся отмеченным неприменённым. Для drum kit нужно хранить явную таблицу MIDI note ↔ imported pad; сдвиг программы в другой банк не должен менять звучащие инструменты при следующем импорте.

Sustain CC64 и pitch bend нельзя молча выбросить при импорте мелодии. Для каждого binding задаётся capability: поддержанный controller импортируется в automation/message lane, неподдержанный отмечается до применения. Допустимый fallback для sustain — явно выбранная материализация эффективной длительности нот; при этом сохраняются данные источника и указывается изменение представления. Преобразование CC в Synth/FX parameter требует явной map; иначе CC остаётся external MIDI lane.

Export по умолчанию SMF1: музыкальная партия → track, tempo/signature → conductor track, абсолютный pitch/velocity/duration сохраняются. MIDI CC/pitch bend экспортируются при поддержке. Внутренняя FX automation не имеет универсального MIDI-эквивалента и попадает в файл только через настроенную CC map; остальное сохраняется в проекте или аудио. Drum export выбирает Original MIDI map или Current pad map; выбор виден до записи файла. SMF0 merge — опция, с проверкой конфликтующих channels/ports. Имена tracks, mappings и неподдержанные meta events нужно исследовать и расширять codec отдельно: текущая модель SMF не гарантирует их полного сохранения.

Работы дополняют этап 3: `program_import*` и `program_manifest*` — compatibility/sample review; новые `midi_import_plan.*`, `program_note_map.*` — таблица назначения и atomic import; развитие `piano_roll_midi.inc`, `midi_file.*`, `midi_file_native.c` — Pattern/Arrangement targets, track names, controller lanes и export scopes. Нужны тесты SMF0 с несколькими каналами, SMF1 с несколькими каналами в track, переезда kit в другой банк, missing samples, occupied pads, duplicate mappings, sustain, bend, tempo map, Save As и MIDI round-trip поддержанных данных.

## Запись и редактирование автоматизации

Автоматизация входит в общую задачу как ещё один вид музыкальных данных, рядом с нотами. Она использует тот же transport, редактирование, перемещение clips, Save/Load и offline export. MIDI CC — один из типов назначения; внутренние параметры Mixer, FX и Synth не следует искусственно ограничивать MIDI-разрешением 0–127.

В текущем коде имеются setters параметров Synth, Mixer/FX control paths и MIDI CC routing. `music_ui.h` также упоминает нативные контейнеры automation events. Это не доказывает наличие готовой общей записи автоматизации новых параметров мода: типы native automation, захват движений и playback contracts требуют отдельного исследования. Нельзя просто записать параметр в неизвестный native event variant, особенно в tag 4 с владением объектами.

Предлагаемая дополнительная модель:

| Сущность | Данные |
|---|---|
| ParameterDescriptor | Стабильный parameter ID, единица, диапазон, default, continuous/discrete, допустимый interpolation, smoothing, rate limit, поддержка live/offline |
| AutomationTarget | Musical instrument instance / Sound / Mixer bus / FX instance / MIDI port+channel+CC; стабильные IDs, отдельно от input knob и номера FX slot |
| AutomationLane | ID, target+parameter ID, область Pattern или Arrangement, режим Read/Off, точки и initial value |
| AutomationPoint | ID, tick, значение в разрешении параметра, interpolation к следующей точке |
| AutomationTake | Armed targets, captured control gestures, transport generation, область перезаписи и исходное состояние для одной Undo-команды |

Каждый параметр явно регистрируется как доступный для automation. В первой версии это разумный проверяемый набор: Synth cutoff/resonance/envelope/LFO/level, Mixer level/pan/send, поддержанные непрерывные FX controls и внешний MIDI CC. Смена FX type, загрузка sample, файловые операции, routing topology, имена и другие операции с аллокациями не становятся автоматизируемыми только потому, что у них есть UI control.

Запись начинается из явного `Auto Arm`, отдельно от разрешения записи нот. Пользователь может записывать ноты, automation или оба вида данных. Записывается применённое музыкальное значение после Pickup/Scaled/Jump и преобразования шкалы; касание энкодера, которое ещё не изменило параметр, не создаёт ложную automation. У точки должна быть музыкальная временная метка из transport input boundary, а не момент очередной перерисовки UI.

Первый набор режимов — Off, Read и Touch. В Touch параметр записывается только во время движения; остальная кривая сохраняется, а после отпускания/завершения жеста возвращается Read с заданным переходом. Write и Latch можно добавить позже: они требуют явного определения полного перезаписываемого участка. Overdub нот не означает суммирование двух кривых одного параметра. Новая take заменяет выбранный интервал данной lane, сохраняя его соседние граничные значения; один жест/take отменяется одним Undo.

Движения нескольких knobs могут записываться одновременно. Поток уплотняется по времени и допустимой ошибке конкретного параметра, сохраняя края, экстремумы и дискретные переключения. Частота и объём ограничены заранее. При переполнении незавершённая take отменяется с сообщением; исходная lane остаётся целой. Записанный playback не захватывается снова как пользовательское движение.

Pattern automation повторяется вместе с Pattern и следует за clip при Move/Copy/Split. Arrangement automation задаёт развитие композиции независимо от повторов Pattern, например общий fade или движение фильтра в течение восьми тактов. В первой версии instance-specific изменение повторяемого Pattern выполняется через Make Variation; отдельный clip automation override можно добавить позже.

Для общих параметров нужен один определённый владелец. Две партии на bus A не могут независимо задавать два значения его громкости в один момент. Bus/Master lanes принадлежат Arrangement; Pattern lanes адресуют собственный инструмент. Если несколько clips всё же адресуют один Synth instance, один FX parameter или один MIDI channel+CC, compiler сообщает конфликт и требует выбрать общую lane/владельца. Порядок обхода дорожек не должен случайно определять звук. Общее правило приоритетов: активный Touch gesture, затем явная Arrangement lane, затем единственная допустимая Pattern lane, затем базовое сохранённое значение.

Playback планирует control events теми же часами, что и ноты. Внутри блока interpolation/smoothing выполняет render adapter в разрешении параметра; UI setters и перестроение FX graph из audio callback не вызываются. Для внешнего MIDI учитываются пропускная способность порта и coalescing CC; Note Off имеет приоритет над плотной automation. При seek вычисляется значение кривой в новой позиции, при loop восстанавливается начало цикла, при остановке первой версии возвращаются базовые значения проекта. Это runtime значения: чтение automation не помечает базовый preset изменённым.

Mixer mute/solo и automation mute — разные операции. Mute музыкальной партии выключает её instrument automation, сохраняя общие Arrangement lanes и необходимые releases. Snapshot для export включает кривые, parameter descriptors и исходные значения. Live и offline должны давать одинаковое управление FX/Synth без зависимости от открытой страницы. Удаление/замена FX instance оставляет явно обозначенную orphan lane; нельзя молча применить её к новому эффекту в том же slot.

На небольшом экране используется дополнительная страница текущего Piano Roll/Pattern editor: `Notes / Auto`. Auto показывает одну lane, имя параметра, шкалу времени и кривую. DATA выбирает точку, K1 меняет время, K2 значение, K3 interpolation; Actions содержит Add/Delete/Copy/Paste/Thin/Clear range. Конкретные жесты уточняются после проверки конфликтов с текущим Piano Roll. Native Events/Steps продолжают работать со своими прежними данными.

## Воспроизведение Horizontal Arrangement

Выбранный подход — компиляция immutable playback plan в объединённый поток с одним владельцем музыкального времени. Это сохраняет существующий audio engine, инструменты и mixer routing. Запуск нескольких штатных sequencer transports не нужен.

Для clip на `start`, с source offset `offset` и циклом Pattern `L` каждое исходное начало `s` получает глобальное время `start + k*L + s - offset`, если оно принадлежит выбранной области источника и окну clip. Play length clip ограничивает число повторов; последний повтор может быть неполным. Полуоткрытые интервалы `[start, end)` исключают двойной On на стыке.

Компилятор должен выдавать native-compatible события и таблицу provenance: arrangement/clip/pattern/event/iteration → occurrence ID и instrument binding. Повторы, probability, choices и velocity сохраняются. Native scheduler решает probability/ratchets один раз; dispatcher использует уже принятые команды. Стабильный порядок равного времени: release прежнего occurrence до retrigger, затем On с детерминированным tie-break.

Первый проверяемый результат — Render to New Sequence для конечной аранжировки, помещающейся в штатные пределы. Он проверяет семантику merge существующим bulk/history adapter. Это промежуточный результат, а не объявление Horizontal playback готовым.

Следующий шаг — private playback sequence/context для такого же объединённого списка, который не появляется в пользовательском Project и не попадает в Save. Без доказательства его создания, привязки и уничтожения не подменять `event_list` указателем и не использовать «свободный» пользовательский sequence slot. Этот native lifecycle — обязательная экспериментальная задача этапа 1b.

Если безопасный private context подтверждён, это основной backend первой версии. Полный поток компилируется перед Play; live edits вступают на следующей безопасной границе через смену immutable generation. Для больших песен позже допускается bounded lookahead с тем же native scheduler, но только после проверки window handoff и held notes. Пока такой backend не доказан, слишком длинная аранжировка получает явный предел, а не обрезанный конец.

Если private context недоступен, запасной путь — адаптер подачи готовых событий в подтверждённую нативную scheduling queue, с единственными штатными часами и sample offsets. Это дополнительный reverse engineering, а не уже существующее API. UI snapshot `step_native_clock_ticks` нужен для экрана; его Timer не годится как точный музыкальный scheduler.

### Границы нот и сэмплов

По умолчанию MIDI duration может выйти за границу цикла Pattern; Off относится к своему occurrence и не переносится modulo на следующую итерацию. При физическом конце clip политика `Cut` выпускает принадлежащие clip ноты; `Carry` разрешает их естественный конец. Для первой версии выбрать Cut на конце clip и Carry через внутренние повторы; пользователь должен видеть эту политику.

Для one-shot sample окончание clip запрещает новые триггеры, но не обрывает уже звучащую волну. Note On/gated sample получает корректный native release; Pad Link, mute groups, choke и loop остаются свойствами инструмента. При извлечении диапазона выбор по умолчанию — события с началом внутри него; удерживаемые ноты, начавшиеся раньше, добавляются только отдельным вариантом «Include held notes» с явным перезапуском от начала диапазона. Воспроизвести sample из середины нельзя обещать без поддержки seek.

Mute/Solo MusicalTrack фильтрует новые On и отпускает её удерживаемые MIDI/gated voices. Audio bus mute остаётся отдельной командой Mixer. One-shot хвосты по умолчанию продолжаются; общий All Notes Off не используется для mute одной партии. На Stop/seek/loop jump сбрасывается старый playback scope. При seek первая версия может начинать без chase нот, начавшихся до позиции, но Off старого scope обязателен.

### Потоки и ресурсы

UI выполняет выделение, редактирование, аллокации и компиляцию. Music owner применяет native commands и управляет occurrence registry. Audio callback получает подготовленный snapshot, sample offsets и ограниченные очереди; там не должно быть malloc, файлового I/O, UI обращений или ожидания mutex компилятора.

Очередь Synth нуждается в acceptance result, резерве для releases и явном overflow recovery. Перевести производителей в одного music owner либо применить доказанную bounded MPSC очередь; простого atomic head недостаточно. Смена snapshot требует отложенного освобождения после quiescence, не только atomic swap указателя.

Начальный продуктовый бюджет можно ограничить восемью видимыми музыкальными дорожками, 1024 clips и 256 активными MIDI occurrences с отдельным реальным лимитом Synth восемь голосов. Это предлагаемая стартовая конфигурация, не измеренная возможность MPC и не привязка дорожек к A–H. До установки лимитов измерить размер структуры, peak compile memory, event density и CPU при FX/sidechain. Capacity failure отклоняет операцию целиком до Play/commit. Voice stealing Synth должен обновлять ownership, чтобы поздний Off украденного голоса не выключил новый.

## Вход в секвенции и монтаж блоков

Оба Song Mode должны поддерживать вход в материал и возврат к тому же месту песни.

### Пустые области и перенос событий

Create Empty Pattern создаёт самостоятельный Pattern заданной длины, например четыре такта, с пустым набором событий. Его можно сразу разместить в Arrange, открыть в существующем Piano Roll и наполнить записью, ручной вставкой или Paste. Это отличается от Gap — незанятого участка timeline, который вообще не ссылается на Pattern. Для обычного Sequential workflow Create Empty Sequence использует проверенную штатную команду создания/очистки нового slot; нельзя очищать существующую пользовательскую Sequence ради создания области.

Copy Events работает между native Sequence, извлечённым Pattern и новой пустой областью через общий clipboard adapter. Пользователь выбирает события либо диапазон времени и партий; Paste вставляет их относительно курсора, сохраняя интервалы, аккорды, duration и velocity. Source origin clipboard задаёт временную точку отсчёта. Есть два явных режима: Merge, добавляющий события к существующим, и Replace Range, заменяющий только выбранную область. Вставленные события получают новые IDs; исходный материал не меняется. Дублирование ссылки на Pattern — отдельная операция, не замена Copy Events.

Если Paste выходит за конец пустого Pattern/Sequence, нужно предложить Extend либо отменить вставку. Не обрезать ноты молча и не переносить хвост в начало без команды Loop. Мappings Sound/InstrumentBinding проверяются до commit; при отсутствии инструмента предлагается назначение назначения, а не автоматическая замена высоты ноты. Связанная Pattern automation переносится по выбору вместе с нотами; Song/bus automation не попадает в чужую музыкальную партию автоматически. Copy/Paste и увеличение длины образуют одну согласованную Undo-операцию.

### Склейка музыкальных блоков

Glue создаёт новый самостоятельный Pattern из выбранных блоков одной музыкальной дорожки, материализуя их source offsets, transpose, repeats, velocity transformations и локальную automation. Время нормализуется к началу выделенного диапазона. Gap внутри диапазона сохраняется как тишина. Два соседних четырёхтактовых clip могут стать одним восьмитактовым Pattern; исходные Pattern IDs остаются в библиотеке. Смена размещений на новый clip выполняется одной Undo-командой после полной проверки результата.

Для двух половин одного события после Split нужно восстановить единое владение нотой без лишнего On и дублирования Off. Для независимо изменённых/перемещённых половин применяются их явные boundary policies; Glue не угадывает, что это одна удерживаемая нота. Локальные кривые сохраняют граничные значения и interpolation. Параметры общего получателя проверяются на конфликты, как при обычной компиляции.

Несколько музыкальных дорожек по умолчанию объединяются Group, сохраняя независимость партий; это не склейка всех инструментов в одну строку. Будущая Merge to New Sequence — явная операция свода музыкальных событий, сохраняющая их instrument bindings и исходную многодорожечную версию. Для native Sequence Split to New Sequences и Glue to New Sequence создают новые slots, проверяют пределы длины и не перезаписывают исходники.

В Sequential пользователь выбирает шаг, вызывает Edit Sequence и попадает в существующий редактор этой Sequence, включая Piano Roll. Вход сохраняет контекст Song: song ID, выбранный шаг и scroll/follow state. Back возвращает к выбранному шагу. Если одна Sequence использована в нескольких шагах, её редактирование меняет все эти использования. Для изменения одного шага команда Make Variation копирует Sequence в новый проверенный доступный slot и заменяет только ссылку данного шага через native Undo-команду. Повторы одного шага по-прежнему ссылаются на один источник. Удобный вход из Song — предлагаемая доработка; готового такого navigation bridge анализ не устанавливает.

В Horizontal пользователь выбирает clip → Edit Pattern → открывается тот же Piano Roll, с breadcrumbs имени Pattern и позиции clip в песне. Начало редактора показывает локальное время Pattern; рядом доступен контекст глобального такта. Для clip с source offset нужно сразу показать его используемый диапазон. Back восстанавливает выделение и прокрутку Arrangement. Preview в редакторе и playback песни не должны удваивать воспроизводимый материал. Редактирование во время проигрывания вступает на следующей безопасной границе; одновременное изменение записываемого материала первоначально остаётся запрещённым.

Для монтажа предлагаются две явно различные операции:

- Split Clip разрезает только размещение на timeline. Оба новых clip ссылаются на исходный Pattern, исходные ноты не переписываются. Для правого clip source offset увеличивается с учётом loop phase; порядок и звучание до следующего редактирования сохраняются. Это быстрый недеструктивный монтаж.
- Управление Split Clip: в Horizontal Arrangement выбрать один блок, поставить курсор внутрь него и нажать физическую **CHOP**. Позиция разреза следует текущему Grid; при выключенном Snap используется точный tick курсора. На границах блока команда ничего не создаёт и сообщает «Cursor inside block». Результат — два независимо перемещаемых блока, правая половина выделена, один Undo восстанавливает исходное размещение. Эта привязка действует только на timeline; внутри Piano Roll и штатного Sample/Chop сохраняются их существующие назначения кнопки. Это проектируемое управление, пока не реализованное в runtime.
- Slice to Patterns материализует левый/правый диапазоны в независимые Pattern IDs. Теперь можно удалить или изменить ноты одной половины без влияния на вторую и на другие использования исходника. Команда Make Variation на одном из разрезанных clips даёт тот же выбор независимо от самого разрезания.

Trim меняет границы clip, Move — его положение, Copy/Paste создаёт новое размещение с тем же Pattern, Duplicate as Variation — новый независимый материал. Delete Clip удаляет размещение, а не Pattern из библиотеки. Удаление используемого Pattern требует отдельной обработки ссылок. Gap между clips является тишиной новых триггеров, а не автоматическим растягиванием соседнего блока.

Разрез на timeline не должен превращать удерживаемую ноту в два Note On. Для ещё соединённых половин compiler сохраняет continuation исходного occurrence и единственный Off. Если половины перемещены независимо, их поведение определяется показанной политикой границ: левая gated/MIDI нота завершается на новом конце, правая по умолчанию не перезапускает ноты, начавшиеся до её source offset. Опция Include held notes создаёт явный новый On; это изменение звучания, а не прозрачный монтаж. One-shot sample может продолжать хвост от левого запуска, но перенос правого clip не даёт произвольного seek внутри аудиофайла. Само разрезание волны остаётся функцией Chop/редактора sample.

Automation при Split сохраняет исходную кривую: в точке разреза вычисляется граничное значение, сохраняется interpolation и состояние перед правым диапазоном. При материализации Pattern обе половины получают необходимые boundary points. Автоматизация абсолютного времени Arrangement не двигается вместе с clip; локальная Pattern automation двигается. Интерфейс должен явно различать эти области.

На одной музыкальной дорожке первая версия запрещает временное перекрытие clips и предлагает другую дорожку; на разных дорожках параллельное воспроизведение разрешено. Это исключает неявное удвоение нот и неопределённое смешивание automation. Отдельная операция Replace заменяет занятый диапазон предсказуемо с Undo.

Пример: восьмитактовый MIDI Pattern → Split Clip на такте 5 → Move правой половины на такт 9 → Make Variation правой половины → Edit Pattern и изменение нот. Оригинальный Pattern остаётся в библиотеке; слева звучит исходный материал, справа — изменённый. Если скопировать левый clip без Make Variation, дальнейшая правка общего Pattern затронет обе его ссылки, о чём редактор сообщает.

## Смешанное отображение и рендер в пэд

Уточнение основного workflow: вокал может оставаться обычным sample на пэде, подготовленным через существующие Trim/Chop. В Song хранится событие запуска этого Sound. Для двух вокальных партий достаточно двух музыкальных дорожек с разными pad bindings; отдельный streaming audio engine не является обязательным условием первой версии.

На одной временной шкале отображаются разные виды материала: нотный Pattern с миниатюрой нот, запуск sample с обозначением пэда и при наличии кэша миниатюрой waveform, результат Render to Pad с waveform и ссылкой на исходный Pattern. Содержимое clip, тип инструмента и вид его отрисовки — отдельные свойства. Дорожки не фиксируются навсегда как Drum/Sample/Synth; имя, цвет и routing принадлежат музыкальной партии.

Визуальная waveform внутри блока не означает, что появилась полноценная Audio Region с seek/time-stretch. Для Pad Trigger начало соответствует событию, а estimated audible extent рассчитывается по sample length, playback/pitch settings и tempo map, когда это возможно; при неизвестной длине она не выдумывается. MIDI gate, длина размещения и длительность звучания sample различаются. One-shot не обрывается автоматически из-за окончания нарисованной ноты. Для looped sample нужно явное прекращение/политика длины. Изменение trim пэда обновляет waveform preview; изменение источника, используемого несколькими событиями, затрагивает все его использования, если сначала не создана копия Sound.

Два длинных вокала могут изображаться протяжёнными блоками в своих строках поверх коротких циклов Drums/Bass/Synth. Это целевое отображение для реально загружаемых native samples, без заявления непроверенных пределов их длины и RAM. Запуск песни с середины по-прежнему требует проверки возможности native sample offset/chase: один On на первом такте не гарантирует корректного вступления вокала при старте с куплета. До поддержки seek такое ограничение показывается прямо, а не маскируется waveform.

### Render to Pad и обратимый Freeze

Render to Pad выбирает Pattern, выделенные события или диапазон одной/нескольких партий; определяет начало/длину и FX policy; рендерит результат в новый WAV; назначает его свободному выбранному пэду и по желанию создаёт на timeline эквивалентный Pad Trigger clip. Оригинальные события сохраняются. Это новый frontend/plan к существующей системе resample/offline export, а не новый независимый DSP renderer.

В основе уже есть `resample_destination.h` с источниками `RESAMPLE_SEQUENCE` и `RESAMPLE_SOUND`, выбором target pad, повторной проверкой занятости и завершением после native assignment/Undo. `resample_stock_backend` владеет native queue/context. `resample_fast_plan` разделяет minimum source duration, musical render length и tail budget. Эти механизмы можно использовать; Render выбранного Pattern/диапазона и обратимый Freeze ещё требуют нового adapter, snapshot и интеграции Synth offline.

Первые два безопасных режима: Render Copy создаёт аудиокопию рядом, не меняя воспроизведение песни; Freeze Clip заменяет только выбранное размещение отрендеренным trigger, отключая его исходный поток без удаления исходного Pattern. Unfreeze возвращает именно этот clip и его binding/automation. Остальные использования исходного Pattern продолжают работать. Нельзя включать оригинал и render одновременно по умолчанию, иначе появится удвоение звука. Назначение WAV, сохранение provenance, замена clip и Undo образуют согласованную операцию; при cancel/failure данные и назначения восстанавливаются.

Dry/With FX требуют явного signal tap. Dry означает рендер источника до выбранной downstream обработки; With FX включает названные ступени. Baked FX не применяются повторно через тот же путь после замены clip. Нельзя глобально выключать bus FX ради одного frozen clip, поскольку другие партии используют эту шину. Если точный эквивалент без повторной обработки в текущем routing невозможен, разрешить Render Copy и явно ограничить Freeze либо подготовить отдельный проверенный маршрут. Sidechain/sends могут требовать проигрывания контекста песни даже при записи одного источника; solo исходника меняет результат.

Musical length и WAV duration хранятся раздельно: четырёхтактовый Pattern с reverb tail может дать WAV длиннее четырёх тактов. Повторы должны сохранять четырёхтактовый шаг и осознанно обрабатывать перекрытие хвостов, а не растягивать ритм до полной длины файла или бесшумно обрезать tail. Для случайных probability/repeats render фиксирует конкретный проход, а живой источник при Unfreeze снова может звучать иначе.

Смешанный clip открывает соответствующий существующий инструмент: MIDI/trigger events — Piano Roll/Events; подготовка звучания audio sample — Sample/Trim/Chop. Freeze clip сохраняет действие Edit Source, возвращающее к исходным нотам через явный Unfreeze/редактирование источника с повторным render; нотные изменения не могут мгновенно изменить уже записанную waveform.

Сначала реализовать Render Copy Pattern → свободный Pad на основе доказанного native render plan; затем Freeze/Unfreeze и рендер диапазона Arrange. Добавить проверки tail, выбранной области, identity источника, project change, occupied target, Undo/Redo, Save As, двойного звучания и двойной FX-обработки.

## Необязательное развитие до полноценных аудиорегионов

Следующий раздел описывает дополнительное развитие, которое не требуется для базового сценария вокала на пэдах. Если понадобятся произвольный монтаж файла на timeline, независимые sample offsets, seek и потоковое чтение длинных записей, можно добавить полноценные Audio Regions. Они могут сосуществовать с короткими повторяемыми Drum/Bass/Synth Pattern. Длина музыкального Pattern не ограничивает продолжительность соседнего вокального clip. Число музыкальных дорожек по-прежнему не связано с восемью bus A–H.

Для этого нужны разные виды содержимого дорожки: Event Pattern и Audio Region. Audio Region хранит asset ID, источник, source offset/length в sample frames, позицию на общей timeline, gain, fade in/out и time-lock policy. Сам WAV не хранится внутри MIDI Pattern/XPJ payload. Save/Save As/recovery проверяют и копируют зависимости проекта; потерянный файл отмечается как missing media, а не заменяется пустым исправным Pattern.

Предполагаемый workflow: Add Audio Track → Import WAV → выбрать Vocal Lead/Double → поставить начало клипа на нужный такт → Trim/Split/Move/Glue → Mixer/FX/automation → Mixdown. Прямая запись вокала в audio track возможна отдельным этапом после исследования существующего Input recorder; возможность импортировать два длинных WAV не означает уже готовой одновременной многоканальной записи.

Обычный native trigger длинного one-shot sample — возможный промежуточный способ воспроизведения от начала. Он не обеспечивает полноценную аудиодорожку: запуск с куплета, перенос правой половины после разреза и loop должны начинать чтение с правильного source frame. Для вокального workflow нельзя считать отсутствие chase/seek приемлемым постоянным поведением. Переход к произвольному такту, pause/resume, loop, mute/solo и offline render являются критериями готовности, а не поздним косметическим дополнением.

Split Audio Region делит ссылки на диапазоны WAV без перезаписи файла; Trim меняет диапазон. Glue соседних частей может создать composite region со списком source ranges; исходные WAV остаются целыми. Создать один новый WAV — отдельный Consolidate/Render с включением или исключением FX по явному выбору. Один длинный файл не должен копироваться в RAM или на SD при каждом разрезании. Небольшие fades и отдельная будущая crossfade-операция предотвращают щелчки при монтаже. Пока перекрывающиеся clips на одной дорожке запрещены, crossfade требует отдельного проверенного режима перекрытия.

Для живого чтения используются общий sample clock, worker prefetch и ограниченные buffers; файловые read/seek не выполняются в audio callback. `pad_sample_source` предоставляет reader для обработки вне audio/UI и не является доказанным realtime streaming backend. Существующие pool/memory sample adapters также не устанавливают безопасный бюджет двух полных вокальных файлов. Сначала исследовать native playback/seek и фактический RAM budget, затем выбирать native-backed regions или streaming adapter. Нельзя обещать минутные лимиты до измерений на устройстве.

Музыкальная позиция Audio Region может быть привязана к такту, но длина источника и source offsets остаются в samples/секундах. Изменение BPM без time-stretch не растягивает спетый вокал. Первая версия явно поддерживает Original Speed и фиксирует политику переноса начала при tempo changes; автоматическое сохранение вокала в долях требует отдельного качественного time-stretch, который не предполагается готовым. До такой поддержки проект должен предупреждать о смещении вокала относительно ритма при смене темпа.

Каждая вокальная дорожка имеет собственные gain/pan/mute/solo, automation и instrument/output binding; обе могут идти на одну шину или на разные, в пределах подтверждённой маршрутизации backend. Bus stems сохраняют смысл шин: отдельные WAV Vocal Lead/Double требуют part/audio-track stems либо разных bus assignments. Offline export должен читать те же audio regions и применять тот же routing/FX, включая sends/sidechain, независимо от физического входа и открытого экрана.

Новый этап Audio Regions добавляется после базового Pattern/Arrange: предлагаемые `audio_region_model.*`, `audio_region_native.*` или `audio_region_stream.*`, `audio_prefetch.*`, развитие asset persistence, `arrangement_compile.*` и offline export. Нужны две длинные mono/stereo вокальные дорожки вместе с MIDI Synth/Drums/FX, чтение с середины, boundaries/fades, пропускная способность SD, low-memory/underrun handling, Save As и совпадение live/offline. Сценарий с двумя файлами по пять минут можно использовать как нагрузочную цель испытания, но не как заявленную поддержку до аппаратного результата.

## Piano Roll и экран MPC

Визуальное требование: новые экраны продолжают актуальные production painters Mixer/MIDI. За основу берутся `mixer_view.c` и `midi_ui.c` выбранной версии, а не старые картинки документации. В основе `a99d474` Mixer использует сетку A–H 2×4, Master в верхнем правом углу, контекстные B1–B3 сверху и три поля K1–K3 снизу. Сохраняются чёрный фон, белые подписи, янтарный `0xffffc247` для фокуса, тёмные поля параметров, плоские списки и существующая индикация Shift/цветов дорожек. MIDI Import/Map следует действующим `heads`, `knob`, `map_paint`, а Pattern/Automation — существующему Piano Roll. Рендер с тестовыми meters и подменным шрифтом обозначается как рендер, не как фотография MPC. Ранее сохранённый `docs/media/mixer/painter-overview.png` показывает старую компоновку и не является актуальным визуальным эталоном.

Сохраняются `piano_roll.c` и его операции. Добавляются event-source adapter, привязка редактора к Pattern ID/revision и вычисление строк абсолютных MIDI notes. `pr_note` сейчас содержит native event, поэтому понадобится отделить музыкальную высоту от native Sound/Tune и расширить encode/commit interface, сохранив действующий native adapter.

### Сохранение действующего управления Piano Roll

Проверенные назначения в `piano_roll_native.inc` основы `a99d474` имеют приоритет над упрощённым демонстрационным управлением макетов. Вход из Song/Pattern должен менять источник событий и контекст возврата, сохраняя этот же обработчик органов управления; не создавать альтернативный Piano Roll input handler.

| Орган управления | Навигация и выделение | Режим Edit |
|---|---|---|
| DATA rotation | В Cursor mode двигает время по Grid; в Notes mode перебирает события. Достижение края автоматически прокручивает вид через `pr_cursor` | Перемещает выделение по времени |
| DATA click | Выделяет событие на отпускании. Shift даёт добавочное выделение | Не переопределять как новый Apply или вход в другой редактор |
| Hold DATA + rotation | Меняет временную границу прямоугольного выделения | Существующее выделение формируется до входа в Edit |
| Hold DATA + fader | Меняет вертикальную границу того же выделения; отпускание DATA завершает жест | Сохраняется исходный набор выделенных событий |
| Fader | Выбирает строку с автоматической прокруткой при выходе из видимой области | Меняет строку/высоту выбранных нот относительно зафиксированных при входе rows |
| Shift + DATA rotation | Горизонтальный zoom вокруг текущего курсора | Zoom остаётся zoom, а не Fine Move |
| Shift + fader | Вертикальный zoom, row height 12–38 | Zoom остаётся zoom, не меняет pitch |
| K1 | Scroll rows | Move, Shift: Fine move с шагом tick |
| K2 | Grid | Pad/Pitch, Shift: Velocity |
| K3 | Scroll time | Length, Shift: Fine length с шагом tick |
| B2 | Начало/конец Range; Shift: Follow | Не назначать сюда новый Auto toggle, вытесняя существующий жест |
| B3 | Edit/Open; Shift: Actions | Apply через существующую history command |
| Shift+B1 | Переключает Notes/Cursor | Отменяет незавершённый preview перед переключением |
| Shift− / Shift+ | Штатные Undo/Redo | Тот же общий history boundary |

`roll_data_begin_move` сохраняет anchor до начала изменения; `roll_data_release` отличает короткое выделение от жеста области. Множественное выделение также использует Shift+pad. В режиме Edit все преобразования являются preview от исходного выделения, а не накоплением ошибок от повторных поворотов/движений фейдера. Нативные защитные проверки записи, ревизии и владения контекстом сохраняются.

В основе обнаружено отдельное несоответствие UI/handler: при Shift подписи K1/K3 вне Edit говорят Zoom rows/Zoom time, но `roll_control` для этих knob CC по-прежнему меняет `top/left`; вызовы `pr_zoom` явно присутствуют на Shift+fader/DATA. Поэтому подписанное knob zoom нельзя выдавать за подтверждённую работающую реализацию. Это отдельная проверка/правка UI, без изменения исходников в рамках дизайна.

Для будущей Auto page предлагается сохранить пространственную логику: DATA — время, fader — значение/выбор lane в явно обозначенном контексте, Shift — масштаб, Hold DATA — область. Конкретные назначения Auto являются предложением. Открытие Auto следует разместить в Actions или выборе слоя, сохранив действующие B2 Range и B3 Edit/Apply.

Открытие clip редактирует Pattern, на который ссылаются его повторы. Команда Make Variation сначала создаёт новый Pattern и переназначает только выбранный clip. При двух клипах исходного Pattern интерфейс явно показывает «Shared pattern»; пользователь видит, где изменение будет слышно. История Pattern и изменения native Sequence проходят через согласованный command boundary; нельзя хранить отдельный скрытый Undo stack, расходящийся со штатным Undo.

На Song входе — компактный выбор Sequential/Arrange. В Arrange экран 320×240 показывает четыре музыкальные строки, прокрутку и 4/8/16 тактов. Блок подписан именем Pattern, длиной и признаком variation; продолжение длинного clip не рисуется как независимый запуск.

Предлагаемая раскладка управления:

- DATA выбирает clip или пустую позицию; в режиме Move перемещает по сетке. Нажатие DATA открывает существующий Piano Roll выбранного Pattern.
- K1 выбирает track, K2 позицию в тактах/долях, K3 длину clip; Shift даёт zoom/source offset/transpose. Изменение Pattern length находится отдельной явно названной операцией.
- B1 Back, B2 Actions, B3 подтверждает действие. Actions содержит Insert/Copy/Paste/Move/Repeat/Make Variation/Extract; опасных действий от одного случайного поворота нет.
- Mute открывает musical track mute/solo; экран подписывает `Parts`, чтобы отличать от Mixer A–H. Пэды выбирают партии, подсветка отражает выбранную/играющую/muted партию.
- В Synth Keys появляется ясное назначение `Audio capture` или `Sequence notes`; это разные виды записи. Rec/Overdub/Play остаются транспортными кнопками.

Назначения жестов предварительные: их нужно проверить против действующего Song/Export, modifier ownership и поздних button-up. Уже применяемые tickets/generations и captured down/up следует расширять, а не обходить.

## Совместимое сохранение

Предлагается одно необязательное поле `amArrangementV1` в существующем архиве, через новый bridge по образцу `mixer_archive.cc`. Оно содержит version, IDs, patterns, tracks, clips, source snapshots, bindings, project Synth preset, tempo/signature map, automation lanes и выбранную Arrangement. Старые native event lists и Song steps не меняют формат. Для automation сохраняются стабильные target/parameter IDs, значения, interpolation и initial state; записи конкретного экземпляра FX не связываются только с порядковым номером его slot. Новые поля проходят version/capability validation до редактирования.

Нет поля — нет Arrangement, работает Sequential, и обычное сохранение не добавляет пустое расширение. Известное поле валидируется полностью перед publish. Future/corrupt payload сохраняется byte-for-byte как opaque, а редактор этого расширения становится read-only. Нативная часть проекта продолжает работать. Не сохранять pointers, node layouts, очередь releases или скомпилированный runtime context.

Поддержанные native events сериализуются через явный versioned codec с сохранением всех нужных полей. Tag 4 и неизвестные виды не преобразуются в tag 3 и не отбрасываются: Extract отказывается от неподдержанного материала с указанием причины. Исходная Sequence остаётся доступной.

Встраивание даёт один native save transaction и сохраняет переносимость файла. Если размер payload или native writer не выдерживает реальные проекты, следующий вариант — sidecar с UUID/generation/checksum и manifest в основном проекте. Новый sidecar сначала записывается и синхронизируется, затем сохраняется ссылка в XPJ; старое поколение остаётся до подтверждения обоих шагов. Два rename не являются общей атомарной транзакцией. Save As копирует связанное поколение и меняет manifest; потерянный sidecar не должен открываться как пустая исправная песня.

Старые версии Am MOD или stock могут удалить неизвестное поле при пересохранении — обратной совместимости чтения native частей недостаточно для гарантии сохранности новых данных в старом ПО. Нужны реальный round-trip и резервная копия расширения при downgrade. Не заявлять поддержку такой записи до проверки.

### Экспорт

Sequential export сохраняет существующий путь. Horizontal live и offline используют один compiled plan и одну политику вероятности/повторов; offline получает собственный transport/render state. Synth рендерится и обрабатывается FX через общий instrument adapter без зависимости от физического Input callback. Начинать с одного Synth instance, явно разделяемого партиями; разные presets на параллельных партиях требуют отдельных instances и нового ресурсного бюджета.

Bus stems A–H/Master Direct сохраняют нынешний смысл. Musical part stems — отдельная опция повторного render с фильтром партий и заранее описанным поведением sends/sidechain. Нельзя получить эквивалент общего звучания простым solo, если компрессор зависит от другой muted партии. External MIDI экспортируется как MIDI; включить его внешний звук в offline Mixdown можно только после аудиозаписи возврата.

У экспорта должен быть задан хвост release/reverb после конца Arrangement и предел его длины. Текущие stems ограничены оставшимися native frames, поэтому автоматическое сохранение произвольного хвоста сейчас не гарантировано.
