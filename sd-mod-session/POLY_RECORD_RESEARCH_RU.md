# Аккорды 16 Levels — исследование 29.10.2026

Кандидат r22b прошёл живую запись двух и трёх нот на настоящем приложении
в QEMU. Ниже сначала приведены исторические наблюдения; итог — в последнем
разделе. Проверка на настоящем MPC ещё требуется.

## Что воспроизведено

При подтверждённых A01 с загруженным звуком, Play → Poly и 16 Levels Tune
две ноты проходят на вход SequenceRecorder как два отдельных события:

```
RECORD type=3 len=0 time=1213 value=78780001 vel=0.795276
RECORD type=3 len=0 time=1213 value=787c0001 vel=0.582677
```

Это наблюдение сделано GDB на настоящем приложении 1.3.0.12 в QEMU,
в точке 0x213ba08. Высоты и velocity различаются. При завершении записи
проверка XPJ по-прежнему не подтверждает сохранение обеих нот.

## Проверенные участки

- Native lookup 0x27cf8d0 сопоставляет события по времени/типу/номеру звука,
  не сравнивая данные высоты. Он вызывается в записи через 0x213aadc,
  а также 0x213a5e0. `check_poly_record.c` выполняет штатный контейнер и
  lookup и воспроизводит конфликт. Кандидат `src/poly_record.c` меняет
  только первый вызов. Разные высоты различаются, перезапись той же высоты
  с другой velocity/длительностью остаётся возможной.
- Изолированный тест проходит, полный preload-конструктор с этим кандидатом
  запускается. Это не означает исправления живой записи.
- Временный опыт в VM с NOP принудительного NoteOff по 0x1e273e0 вместе с
  двумя перенаправленными lookup также не подтвердил полный аккорд. Эти
  дополнительные изменения не внесены в исходники и не входят в пакет.
- Завершение pending-ноты идёт через 0x213b130, вызов из 0x20df4f8;
  поиск pending выполняется по программе/треку/номеру звука. Следующий шаг —
  проверить число NoteOff и соответствие каждой pending-ноте, включая Stop.
  Закрывать все ноты при первом отпускании нельзя: потеряются независимые
  длительности аккорда.

## Воспроизводимость и границы

`build_poly_candidate.py` создаёт только лабораторную библиотеку; ничего на
физическую SD не записывает. Флаг MPC_POLY_RECORD есть только у кандидата.
По умолчанию в остальных сборках он выключен. `--sequence-only` создаёт
кандидат исправления цветов Seq без установки hook записи аккордов.

Файлы наблюдений XPJ: `work/lab-tests/poly-live-*.json`.
Они содержат также невалидные подготовительные пробы с Velocity и пустым A08:
их нельзя считать доказательством поведения Poly/Tune с загруженным сэмплом.
Подготовленный корректный экран — `poly-source-prepared.png`, отдельный
результат — `poly-live-a01-experiment.json`.

Для готового исправления ещё нужны две/три ноты одного звука, раздельные
velocity/длительности, Mono/Poly, Undo, Save/reopen и подсветка при воспроизведении.

## Найден дополнительный монофонический обработчик

Обработчик 0x1a85bc0 хранит единственный последний пэд в объекте+0x3d8.
При новом ненулевом нажатии другого пэда (0x1a85c3c..0x1a85c84) вызывает
0x1e270d0 для предыдущей ноты. Отпускание обрабатывается только при совпадении
пэда с последним (0x1a85c04..08 → 0x1a85cc0). Запуск нового пэда идёт через
0x1a85990; вызов Input 0x1e27360 находится в 0x1a85a70.
Это следующий конкретный участок для Poly-aware изменения; простой NOP
одного NoteOff не заменяет учёт всех удерживаемых пэдов и их отпусканий.
Нужно сохранять отдельные длительности при произвольном порядке отпускания.

Попытка вызвать installer вручную из GDB в уже работающем госте завершилась
ошибкой возвратного breakpoint GDB (0xc2d180) и падением лабораторного процесса.
Защитный загрузчик вернул штатное приложение. Это не аппаратный сбой;
никакие операции с настоящим MPC не выполнялись. В дальнейшем устанавливать
hook только конструктором до main и запускать новую копию, как в стенде
check_resample_bootstrap; не вызывать installer через GDB в живом приложении.

## Исправление r22b и проверенные результаты

Фактический вход живых пэдов — 0x1545050, а не обработчик экранного выбора
0x1a85bc0. Это подтверждено breakpoint на Audio Processing thread.
Первый вариант, изменявший только экранный обработчик, не исправлял живую игру.

В Poly/Tune новый обработчик строит штатное событие через 0x27e54d0 и
0x21472f0 и передаёт его обычному Engine 0x211b090. Mono и остальные типы
16 Levels сохраняют прежний обработчик. Poly читается по Instrument+0x1690;
это поле подтверждено штатной записью Polyphony/Mono в 0x2801af4..1b30.
UI публикует только числовой снимок; указатель Instrument не хранится в аудиопотоке.

У штатного Engine одна отметка удержания на исходный звук: первое NoteOff
удаляло маршрут, необходимый второму отпусканию. Для каждого отпускания теперь
заново разрешаются действующие Track и ClipRecorder через 0x20f8da0/20e2290.
В очередь записи идёт обычный 0x20e4da0 с временной меткой высоты в аргументе
NoteOff. Метка удаляется до вызова штатного завершения 0x213b130; в события,
аудиоданные и XPJ она не попадает. Выбранная pending-нота переставляется в начало
родного списка и закрывается штатной функцией с её собственной длительностью.
Общий звуковой NoteOff отправляется после последнего физического отпускания.
Это означает общее живое отпускание Gate; записанные длительности раздельные.

Помимо lookup финального списка, отдельный lookup 0x27cfcd0 внутри 0x2137ed0
схлопывал разные высоты при объединении изменений для Undo. Исправлены только
вызовы записи: 213aadc, 213a5e0, 2137f58, 2137c44. Общие компараторы движка
глобально не заменяются. Нативный отрицательный контроль воспроизводит
схлопывание Undo-batch до одного события; исправленный batch сохраняет два.

Полная VM, библиотека e9da5405780868818eb97c91f0722331c949bdd8917155228d9404831299bc9a:

- две ноты одного звука в позиции7200: velocity74/101, длительности1106/1932;
- три ноты в позиции1920: velocity55/74/101, длительности470/821/1296;
- во всех пробах ноты отпускаются в обратном порядке;
- Undo удаляет двухнотный аккорд целиком, Redo возвращает обе ноты;
- при проигрывании маски пэдов 0088 и 0888 показывают соответственно обе
  и все три ноты;
- Mono проверен по фактическому экрану Play → Mono и обычной записи одной
  ноты: velocity90, длительность1064.

Данные: work/lab-tests/poly-final4-reverse.json, poly-three-final.json,
poly-undo-redo.json, poly-playback.log, poly-three-playback-final.log,
mono-real-result.json, poly-real-mono.png. Невалидная более ранняя проба
mono-prepared показывала Lights и не считается проверкой Mono.

Исправлен и лабораторный читатель XPJ: нельзя брать первый элемент sequences
(родной cereal map не отсортирован). Учитывается currentSequence; пустая
секвенция может отсутствовать в map. Для проверок сохранённого A01 его ключ
разрешается явно, поскольку autosave не обновляет выбор экрана немедленно.
Чтение ждёт завершённого gzip/JSON; копировать Temp-Project во время его
перезаписи нельзя. Эти изменения относятся к тестовому стенду, не к MPC.
