# USB-зарядка: найден аппаратный тракт, 29.10.2026

**Рабочий режим зарядки пока не реализован.** Получено новое основание для
исследования: зарядкой управляет код контроллера панели, а не найденный ранее
Linux-узел `mains-power`. В просмотренных обработчиках штатного протокола
команда независимого запрета зарядки не найдена. Это не доказывает отсутствие
любого другого интерфейса и не подтверждает работу USB Audio при запрете зарядки.

## Откуда получены сведения

Только статический разбор оригинального файла:

`part3/usr/share/Akai/AC50/Firmware/AC50/UpdateImage.rbin`

Размер — 77784 байта; SHA-256:
`73cb081b24dfe85549ffcd92730c19762058b848c77cf45f3dfa0ec0ac01a9f4`.

Он состоит из двух контейнеров `!Rbn`: по смещениям `0` и `0x55ec`.
У каждого три сегмента с отдельными файловыми смещениями и адресами загрузки.
Для второго контейнера сегмент кода/данных находится в файле по `0x5718`,
адрес загрузки `0x0800f100`, длина `0xd8b8`.
Числовые версии заголовков — 1.0.0.22 и 1.0.0.51. Это версии вложенных образов;
они не заменяют версию приложения MPC 1.3.0.12 и не измерены на устройстве.

Файл обновления **не запускался и не отправлялся устройству**. Его содержимое
и дизассемблированные листинги не включаются в Git. Изменения прошивки MCU
не входят в согласованный непостоянный SD-мод.

## Датчик аккумулятора

По адресу MCU `0x0801aa00` находится встроенный сценарий настройки датчика.
В нём проверяются `DEVICE_TYPE=0x0427` и `FW_VERSION=0x0202` для I2C-адреса
записи `0xaa` (7-битный адрес `0x55`). Эти значения точно совпадают с
[BQ27427 Technical Reference Manual, §5.1.2–5.1.3](https://www.ti.com/lit/ug/sluucd5/sluucd5.pdf).

Это основание идентифицировать датчик в поставляемом коде как BQ27427.
Это измеритель состояния аккумулятора; его команды сна/сброса нельзя выдавать
за выключение зарядки. Отсутствие датчика в Linux power_supply теперь понятно:
в исследованном коде с ним работает MCU. Физическое соединение шин отдельно
на плате не проверялось.

## Зарядный контроллер

Инициализация по `0x0800fcae` записывает I2C-адрес `0xd6` (7-битный `0x6b`)
в отдельный контекст `0x200004c0`. Драйвер MCU читает 11 регистров;
таблица полей по `0x0801bd26` содержит 39 записей «регистр / сдвиг / ширина».
Адрес и распределение полей совпадают с семейством BQ24296/BQ24297:

| Поле таблицы | Регистр и биты | Назначение по документации TI |
| --- | --- | --- |
| 0 | REG00[7] | EN_HIZ — вход в высокоомное состояние |
| 5 | REG01[5] | OTG_CONFIG — питание USB в обратном направлении |
| 6 | REG01[4] | CHG_CONFIG — разрешение зарядки |
| 26 | REG07[5] | BATFET_DISABLE — отключение батарейного силового ключа |
| 28 | REG08[7:6] | VBUS_STAT — состояние входного источника |
| 29 | REG08[5:4] | CHRG_STAT — стадия зарядки |

Источник: [BQ24296/BQ24297 datasheet, §9.6](https://www.ti.com/lit/ds/symlink/bq24297.pdf).
Точная маркировка микросхемы на плате не прочитана; совпадение семейства
не следует превращать в утверждение о конкретной модели.

CHG_CONFIG — подходящий по назначению отдельный бит. EN_HIZ, BATFET_DISABLE,
OTG_CONFIG и выключение USB gadget не являются равноценной заменой.
Наличие бита ещё не даёт приложению Linux способа безопасно его изменить.

## Почему нельзя просто добавить переключатель

В MCU функция по `0x08011f94` меняет поле в буфере регистров, затем драйвер
отправляет обновлённые значения контроллеру. Автономный цикл питания по
`0x0800ff84` снова рассчитывает режим зарядки по своим условиям.
Вызов `0x080101ca` устанавливает поле 6 (CHG_CONFIG); обе ветви передают
значение, выбранное самим MCU. Однократная посторонняя запись не означает
устойчивую политику Standard / Low Battery.

Просмотрены обработчик MIDI CC `0x080170bc` и обработчик SysEx
`0x080149e4`, включая таблицу обычных параметров по `0x0801bdd0` и
обработчики чтения/записи `0x08014d84` / `0x08014dc6`.
В просмотренном пути не найден параметр, который передаёт запрет зарядки
в автономный цикл. Таблица содержит 10 групп параметров с нулевыми callback;
объявлять одну из них режимом зарядки без доказательства нельзя.
Полный формальный анализ всех путей исполнения MCU не выполнялся.

Таким образом, ограничение сейчас — доступ из Linux к политике MCU.
Перезапись MCU ради этой функции не производится. Не доказано, что она
неизбежна: остаётся возможность другого штатного интерфейса, который пока
не обнаружен. Повторять прежний sysfs-отчёт или запускать QEMU для проверки
зарядного тока смысла нет: нужный аппаратный тракт там не моделируется.

## Что нужно до внедрения

Нужен подтверждённый интерфейс AC50 для изменения только разрешения зарядки:
документированная команда, соответствующий обработчик MCU либо аппаратная
схема, подтверждающая другой доступный путь. После этого потребуются чтение
фактического состояния, проверка тока, восстановление штатной политики при
Mod Off/сбое и проверка приёма **и** передачи USB Audio на устройстве.

При таком управлении отключённая зарядка аккумулятора не обязательно означает
нулевой ток от USB: отдельно остаётся потребление работающего устройства.
Не следует обещать работу исключительно от батареи без аппаратного измерения.

## Воспроизводимая проверка

`inspect_power_mcu.py` читает только переданный локальный Rbin и печатает JSON.
Внешних Python-зависимостей нет. Он проверяет точный SHA-256, границы
контейнеров/сегментов, извлекает таблицы и проверки идентичности датчика.
Хранящиеся в контейнере CRC выводятся как исходные значения, без утверждения
об их проверке. Скрипт не открывает MIDI/I2C/USB и ничего не пишет на устройство.

```powershell
python inspect_power_mcu.py "..\extracted_v1.3.0\partitions\part3\usr\share\Akai\AC50\Firmware\AC50\UpdateImage.rbin"
```

Проверено на исходном файле: два контейнера, по три сегмента, датчик 0x0427,
поле 6 = REG01[4]. Усечённый контейнер, неверная сигнатура, неизвестный хеш
и чтение незагруженной области отвергаются. Это проверка исследования,
а не аппаратный тест режимов зарядки. Выпуск r23a и файлы карты не менялись.

## Проверка исполняемого кода MCU в изолированной модели

`check_power_mcu_policy.py` запускает исходные Thumb-функции из того же
проверенного образа в Unicorn 2.1.4. Код SysEx-диспетчера, обработки параметров,
таблицы регистров и расчёта политики не заменён собственной реализацией.
Таймер, готовность датчиков, напряжение/SoC, доступный ток источника,
физические кнопки и операции обмена с периферией подставлены стендом.
Обновление светодиодов отдельно пропущено. Это модель отдельных функций,
а не полная эмуляция MPC или электрического зарядного тракта.

В основном сценарии прибор условно включён, источник сообщает 1500 мА,
VBUS присутствует, датчик сообщает 3800 мВ / 50%, ошибок и нажатий нет.

| Проверка | Наблюдение в памяти эмулятора |
| --- | --- |
| Первый расчёт политики | CHG_CONFIG устанавливается в 1 |
| Сброс CHG_CONFIG штатной функцией записи поля | Сразу читается 0 |
| Следующий расчёт политики | CHG_CONFIG снова равен 1 |
| Запись параметров 0–9 через исходный обработчик SysEx 0x6c | Прочитано записанное значение; после расчёта CHG_CONFIG = 1 |
| Нет источника, исходно CHG_CONFIG = 1 | Политика сбрасывает его в 0 |
| CURRENT_MODE_DETECT = 2, режим charge-through accessory (500 мА) | Политика сбрасывает CHG_CONFIG в 0 |

Для каждой из десяти групп проверено только значение `default + 1`, все
они приняты обработчиком. Полный диапазон значений и все комбинации команд
не перебирались. Этот тест не доказывает отсутствие любого другого интерфейса.
Последние две строки — отрицательные контрольные случаи: стенд действительно
исполняет условный расчёт, а не всегда возвращает «зарядка включена».

Уточнение после разбора Type-C: 500 мА в этом тесте соответствуют специальному
режиму charge-through accessory, а не произвольному обычному USB-порту на
500 мА. Прежнее обобщение про любой слабый источник было неточным.
Переносить этот результат на конкретный кабель/телефон нельзя.
Потребление от телефона при отключённой зарядке батареи здесь не измерено.

Повторение локального стенда:

```powershell
python -m pip install --target work/power-research/python-deps unicorn==2.1.4
python check_power_mcu_policy.py "..\extracted_v1.3.0\partitions\part3\usr\share\Akai\AC50\Firmware\AC50\UpdateImage.rbin" --dependency-path work/power-research/python-deps
```

Проверка завершена `PASS`. Все периферийные записи находятся только в памяти
эмулятора; реальные MIDI, USB и I2C не открываются. Проверки зарядного тока
и USB Audio на устройстве этим результатом не утверждаются. Режимы зарядки
не добавлены: для корректного внедрения всё ещё нужен подтверждённый вход
управления политикой MCU из приложения.

## Оставшийся путь через контроллер Type-C

Таблица по `0x0801bda9` и адрес `0x60` совпадают с TUSB320/TUSB320I.
Точная маркировка на плате не прочитана. В драйвере есть отдельные поля:

| Поле | Адрес | Доступ по документации TI | Что означает |
| --- | --- | --- | --- |
| CURRENT_MODE_ADVERTISE | 0x08[7:6] | RW | Ток, объявляемый источником DFP |
| CURRENT_MODE_DETECT | 0x08[5:4] | RU, чтение с аппаратным обновлением | Возможности подключённого источника, обнаруженные приёмником UFP |

Источник: [TUSB320 datasheet, §7.3.1.2, §7.3.2 и §7.6](https://www.ti.com/lit/ds/symlink/tusb320.pdf).
Управление ADVERTISE не является ограничением потребления устройства UFP.
Менять роль порта или его подключение ради этой задачи нельзя считать
проверенным способом сохранить USB Audio.

Штатный MCU получает доступный ток через `0x0800fb04`: читает именно
DETECT, затем таблицу 16-битных значений по `0x0801a9f8`:

| DETECT | Значение в коде MPC | Значение режима по TI |
| --- | --- | --- |
| 0 | 900 мА | Default; это выбранная прошивкой трактовка, не универсальная гарантия тока USB |
| 1 | 1500 мА | Medium |
| 2 | 500 мА | Charge-through accessory |
| 3 | 3000 мА | High |

Стенд дополнен исходным getter DETECT и таблицей тока, без подстановки
результата функции `0x0800fb04`. Все четыре режима дали указанные значения.
При DETECT=1 изменение ADVERTISE 0–3 в имитируемом кеше не меняет
обнаруженный ток или рассчитанное разрешение зарядки. Проверенные SoC
2/14/15/50/100 при том же источнике также оставляют CHG_CONFIG=1;
это не готовая политика Low Battery. Реальный зарядный ток и завершение
зарядки при полном аккумуляторе такими значениями бита не определяются.

Текущий вывод: найденный Type-C-путь тоже не даёт приложению настройки
«не заряжать», а подмена USB-дескрипторов не изменяет читаемое MCU поле CC.
В известном Linux-отчёте устройства Type-C-контроллер 0x60 не представлен.
Для продвижения нужен новый подтверждённый интерфейс к MCU/зарядному
контроллеру либо схема платы, подтверждающая другой программно доступный путь.
Наличие такого пути пока не доказано; отсутствие всех возможных путей
этим исследованием также не утверждается. Рабочая сборка r23a не изменена.

## Дополнительная проверка Linux, 30.10.2026

Проверены служебные библиотеки `libaz01-prog`, `libaz0x-info`, `libaz0x-splashctl`,
`libaz0x-webserver-client`, служба `az01-pwrbtn`, правила udev/systemd и
применимые модули ядра из того же rootfs.

- В экспортируемом API `libaz01-prog.so.1.3` есть `az01_get_power_source`
  (0x66a0), но setter зарядки не найден. Есть запрос `getvar:power-source`
  и пути чтения `/sys/class/power_supply/{az01-ac-power,mains-power}/online`.
  Проверенная функция чтения по 0x4eb0 открывает путь с O_RDONLY, читает один
  байт, сравнивает с `1` и закрывает файл. Это проверка наличия внешнего питания,
  используемая в том числе перед обновлением, не управление зарядкой.
  Дополнительно просмотрен общий `az01_set_flag` (0x67d0): это диспетчер
  операций, а не setter зарядки. В обработчике по 0x7d60 единственный
  принятый флаг 0 формирует `oem set-flag:program-fuses`; это не управление
  батареей. Эта операция не вызывалась.
- `libaz0x-info.so.0.7.1` читает свойства платы, накопителя и загрузчика.
  В просмотренных строках и API команд зарядки не найдено.
- `az01-pwrbtn` обслуживает событие кнопки и вызов poweroff; не является
  зарядным daemon.
- В фактическом DT узел `/serial@fe670000/control-surface` совместим с
  `serial-midi`. У `snd-serial-generic.ko` проверены операции raw MIDI/serdev;
  отдельного ioctl зарядки в просмотренной таблице символов нет.
- `inmusic-cs.ko` — другой драйвер ввода через SPI (кнопки/энкодеры).
  `snd-soc-inmusic-az07.ko` — аудиокодек с GPIO mute/reset. Их имена и наличие
  GPIO не дают основания использовать эти линии для зарядного контроллера.
- Существующий живой отчёт `MPC_POWER_AUDIT.txt` по-прежнему показывает
  generic-adc-mains и I2C-устройства rk817/rk8602/ak4558/at8563s. Отчёт заново
  на MPC не запускался. Присутствие rk817_charger.ko в rootfs не доказывает
  подключения батареи MPC к его зарядному тракту.
