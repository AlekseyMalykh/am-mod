# Stage 4a — модель Horizontal Arrangement и подготовка событий

Первая часть этапа 4 реализована в `arrangement.h/.cc`. Она использует
готовые `Library`/`Pattern` этапа 3, не создаёт второй Piano Roll и не
запускает новый sequencer clock. Пока это изолированный control-owner модуль:
в приложение/экран/архив и native transport он ещё не подключён.

## Данные и операции

- Arrangement имеет длину в native ticks (960 ticks на четверть), revision
  и стабильные ID. Tempo и музыкальный clock остаются у штатного транспорта.
- Музыкальная строка хранит имя, mute/solo. ID строки не является ни MIDI
  channel, ни pad bank, ни mixer bus A–H.
- Block хранит `pattern ID`, `track ID`, start, length и source offset.
  Length может превышать длину паттерна: source phase повторяется, события
  в хранилище не дублируются. Разные строки могут играть одновременно.
- Реализованы add/copy/move/resize/delete blocks, mute блока, mute/solo строки
  и изменение длины песни. Невалидная операция оставляет данные/revision/ID
  counter и выходной аргумент нового ID неизменными.
- На одной строке блоки не перекрываются; соседние разрешены. Для наложения
  нужны разные строки. Эта первая политика исключает неоднозначное двойное
  воспроизведение; UI ещё должен показать соответствующий отказ.

`cut_clip(id, cursor, ...)` — готовая операция будущего Chop на курсоре.
Курсор должен лежать строго внутри блока. Левая часть сохраняет ID,
правая получает новый ID и phase `(offset + left_length) mod pattern_length`.
Границы onset полуоткрытые: нота в точке разреза принадлежит правому блоку.
Удерживаемая нота с onset слева сохраняет duration, справа не запускается
повторно. Это перенос gate, не seek внутри записанного аудио.

Join сейчас соединяет соседние блоки одной строки/паттерна с совпадающей
фазой и mute state. Для склейки разных паттернов нужна отдельная операция
создания объединённого Pattern; она ещё не реализована. Вариации создаются
прежней библиотекой, новые блоки затем смогут ссылаться на их ID.

## Подготовленный поток

`prepare_arrangement` разрешает Pattern IDs через Library и готовит один
упорядоченный поток значений `ScheduledNote`. Для примера 2/4/8 тактов один
двухтактовый блок ударных длиной восемь тактов даёт четыре прохода исходного
паттерна, четырёхтактовый — два, восьмитактовый — один. В runtime-хранилище
до подготовки это по-прежнему три ссылки на три исходных паттерна.

Сохраняются velocity, MIDI channel bits, probability, Note Repeat, gate,
Tune/Chop и остальные известные inline flags. Модель не решает случайную
вероятность и не эмулирует Sample/Synth DSP. Она передаёт значения будущему
native adapter. Инструментальная цель — Program key + pad + source note;
снимок mixer bus из Pattern не превращается в правило аудиомаршрутизации.
Native adapter должен заново проверить/разрешить актуальную Program/pad
mapping, а Mixer/FX сохраняют свою собственную маршрутизацию.

Onsets включаются только в [block.start, block.end). Нота может закончиться
за границей блока/песни. Живые mute/solo/Stop должны затем корректно снять
принадлежащие транспорту голоса; статический compiler этого ещё не делает.
Если строка muted, она исключена; при наличии solo включаются только solo
строки, mute имеет приоритет. Muted block не даёт новых onsets.

Количество событий вычисляется до выделения итогового массива, без обхода
каждого заведомо недопустимого повтора. Бюджеты: 32 строки, 512 блоков,
32768 подготовленных нот, 1024 инструментальных цели. Все allocations и
sort выполняются до playback, вне audio callback. Output содержит только
собственные значения. При отказе/исключении прежний output сохраняется.

Prepared snapshot содержит project epoch, arrangement revision и library
revision. `matches` отвергает данные другого проекта/версии; исчезновение
используемого паттерна даёт stale, без обращения к освобождённому объекту.
Будущий bridge должен запретить удаление используемого Pattern либо явно
обновить ссылки одной общей транзакцией. Сам Store этапа 3 пока не изменён.

## Почему Sequential Song не меняется

Текущий `song_ui.c` работает со штатным списком пар sequence/repeats.
Он не представляет параллельные блоки разной длины. Новый value model
готовит общий поток без требования запускать несколько native sequences
одновременно. Пока ни список Sequential Song, ни его editing/export,
ни project data не меняются: новый модуль даже не включён в preload builder.

Следующая часть этапа 4:

1. Общий project Store/архив Arrangement + Pattern references, проверки
   удаления и stale publication.
2. Переключатель Sequential/Arrange и timeline в SongScreen. Связать Chop с
   `cut_clip`, открытие блока — с существующим pattern editor. Сохранить
   текущие аппаратные действия Sequential и управление encoder/fader.
3. Native adapter подготовленного потока. Проверить ограничения длины
   штатной Sequence и представимость инструментальных целей до публикации.
   Первое включение — только на безопасной границе остановленного транспорта;
   live edits, voice ownership, длинные хвосты и экспорт требуют отдельных
   native/QEMU сценариев. Никакие события сейчас в движок не инжектируются.

## Проверки

`verify_arrangement.py` собирает только отдельные test executables: host,
host ASan/UBSan, ARM QEMU, ARM UBSan. Проверены:

- Совместное размещение 2/4/8 тактов и единый поток из 12 событий.
- Равенство музыкального потока до/после cut/join внутри повторов и длинных
  gates; отсутствие лишнего onset на разрезе sample.
- Copy/move и транзакционный отказ перекрытия/невалидных границ.
- Mute/solo, удалённый Pattern, несовпадение project/revisions.
- Лимит 32768: точное значение проходит, 32769 отклоняется до подготовки.
- 26 allocation failures: старый output не меняется.
- Library, исходные Pattern и их события не меняются после операций блоков.

Proof/logs/hashes: `build/arrangement/verification.json`. Ни UI, ни реальные
аудио/MIDI playback/Stop, save/load Arrangement и аппаратный MPC этим не
проверены. Приложение/preload/пакет не собирались.
