# Основания первой доработки, MPC Sample 1.3.0.12

23 октября 2026. Проверяемый бинарник имеет SHA-256
`b6584cba76e416e432ad202509099d34373dc2c3d6a8fb625f5678bf0193b508`.
Все адреса ниже — виртуальные адреса относительно базы PIE; в сегменте RX они
совпадают с файловыми смещениями.

## Исправление r2 после физической пробы r1

Физическая проба r1: пользователь увидел янтарное значение K2, затем нажатие
энкодера погасило экран. Журнал подтверждает SEGV в 10:57:17 UTC и возврат
штатного процесса в 10:57:24 UTC. Прошивка не перепрошивалась.

В r1 была ошибочная инструкция `ldr x19,[x0,#0x40]`: указатель callback
считался объектом слушателя. На самом деле `0x16541a0` получает **сам screen**:
оригинальный код `0x16541ac` читает `[x0,#0x108]` напрямую. Объект слушателя
получает другой, соседний callback `0x1654180`; смешение этих двух соглашений
и привело к ошибке. В r2 инструкция заменена на `mov x19,x0`; остальные
604 байта вставленного кода сохранены.

Прежняя проверка передавала синтетический listener и повторяла ошибку патча.
Её результат не подтверждал реальный контракт вызова. Новая проверка сначала
выполняет неизменённый штатный callback с прямым screen, затем с теми же
аргументами — новый callback. Кроме того, сохранённый машинный код r1 запускается
в изолированном дочернем процессе с теми же аргументами и воспроизводит SIGSEGV.
R2 проходит прямой/обратный обход и остальные сценарии при двух базах PIE.
На физическом устройстве r2 ещё не проверена.

Обновление после следующей физической пробы: r2 отработала 180 секунд без SEGV.
PRECHECK_BEGIN 11:05:36 UTC, CLONE_START_REQUESTED 11:05:56,
запуск процесса подтверждён в 11:05:59. В 11:08:56 systemd записал
`Service reached runtime time limit`; штатный процесс восстановлен в 11:09:04.
Пользователь подтвердил появление значений, но указал неверный смысл цвета
и возможность нескольких жёлтых значений. Последнее погасание было возвратом
по таймеру, а не повторением сбоя r1.

## Цвет r3

Жёлтый разрешён только при совпадении глобального фокуса
(`0x723cde0`, тот же указатель, который читает штатный get_focus `0x2d74550`)
с `slider + 0x1d8`, установленном флаге временного значения и режиме просмотра.
Все остальные значения используют штатный цвет.

Режимы различаются текущим интервалом уже существующего таймера:
просмотр энкодером — 2000 мс, изменение значения — 2001 мс. Для пользователя
оба срока составляют примерно две секунды; разница в 1 мс служит локальным
признаком режима и не меняет аудио/параметры. Это позволяет не вводить новое
поле в неизвестную структуру компонента или сохраняемый указатель на компонент.
Штатный startTimer в `0xff93c4` записывает interval в `timer + 0x10`,
stopTimer `0xff1c4c` обнуляет его. Поэтому чтение `slider + 0x208` использует
существующее поле, а не предполагаемое свободное место в объекте.

Изменение значения, включая обновления из свойств, проходит через уже найденный
вызов `0x3b7d360`, который назначает 2001 мс внутри Sample. Поэтому обновлённые
при загрузке значения также не становятся жёлтыми. Смена фокуса проверяется при
каждой отрисовке; штатный focus setter перерисовывает старый и новый компоненты.
Проверки дополнены сменой режима без смены фокуса и несколькими одновременно
установленными флагами/таймерами: жёлтым остаётся максимум текущее значение.

## Найденные штатные механизмы

В отличие от предварительной карты `docs/research/ENCODER_VALUE_PEEK_PATCH_MAP.md`, для этой
реализации нужен **ui::Slider**, а не ui::ValueLabel. На Sample параметры связаны
со Slider; ValueLabel используется, в частности, в других экранах.

| Точка | Подтверждение в коде |
|---|---|
| `0x16541a0` | Булевый callback Sample: при true вызывает обход фокуса `0x15c1490`, направление читает из `screen->controls + 0x22a0`. Оригинальный BTI остаётся на месте; заменён следующий переход. |
| `screen + 0x99c0` | Контейнер фокуса; в `+0x70/+0x78` начало/конец текущего вектора HWFocusable*. Обход подтверждён полной функцией `0x15c1490`. |
| `0x6e212a0` | Основной vptr SampleModeScreen. Перед собственным показом проверяется точное совпадение. |
| `0x706e5d0 / 0x706e800` | Основной vptr ui::Slider / его HWFocusable base, смещение base `+0x1d8`. Подтверждены конструктором `0x3b7dfd0`. |
| `slider + 0x230` | Флаг временного значения: `0x3b7d35c` устанавливает; LookAndFeel `0x15cde04` выбирает форматированное значение при true. |
| `slider + 0x1f8` | Штатный Timer. Конструктор `0x3b7e04c..0x3b7e08c`, callback `0x3b7d2f0` очищает флаг, останавливает таймер и вызывает repaint. |
| `0xff9370 / 0xff1bc0` | Штатные startTimer / stopTimer, используемые компонентом. |
| `0x3b7d360` | Исходный вызов startTimer(500) после изменения значения. Перенаправлен на выбор 2000 мс для Slider внутри Sample. |
| `component + 0x18` | Родитель Component; подтверждён чтением и записью в addChildComponent `0x1178f00`. Поиск предка ограничен 32 переходами. |
| `0x15cdeb4` | Получение цвета в ветке отрисовки активного форматированного значения; новая функция возвращает ARGB `0xffffc247` только при установленном флаге внутри Sample. В остальных случаях вызывает штатный findColour `0x1131fa0` с исходными id и inherit=false. |

Показ переиспользует полностью штатный путь форматирования/отрисовки. В новой
функции нет вызовов изменения параметров, генерации звука, сохранения проекта,
выделения новых компонентов, фоновых потоков или хранящихся между событиями указателей.
Таймер принадлежит самому Slider, как и в штатном приложении. При переключении
страницы скрытый компонент может закончить свой двухсекундный таймер штатным
образом; отдельного отложенного callback мода нет.

## Размещение кода

Первый PT_LOAD исходного ELF: offset/VA 0, RX, filesz=memsz `0x6d3aff8`.
Следующий PT_LOAD начинается в файле `0x6d43bb0`, VA `0x6d53bb0`.
Между ними 35768 нулевых байт; сборка проверяет весь этот промежуток.
Новые 640 байт r3 начинаются в `0x6d3b000`; длина первого PT_LOAD увеличивается
до `0x6d3b280`. Второй сегмент, его смещения, TLS, релокации и размеры файла
не меняются. Все новые переходы ARM64 укладываются в непосредственный B/BL.
ADRP/ADD остаются относительно общей базы PIE; абсолютных указателей в коде нет.

В штатном BusyBox `dd` не поддерживает conv=notrunc; проверка на одноразовом
файле показала усечение файла при записи с seek. Поэтому он не используется.
Собран небольшой ARM-помощник `apply-peek`: он не принимает путей или других
аргументов и открывает только `/run/mpc-clone-trial-v1/MPC-Sample` с O_NOFOLLOW.
До записи проверяет tmpfs, обычный файл, владельца root, единственную жёсткую
ссылку, точный размер и исходные байты всех изменяемых участков. Запись через
pwrite сохраняет длину файла. До запуска и после записи проверяются SHA-256
помощника и полной RAM-копии. Ошибка на этом этапе не останавливает штатный процесс.

## Что проверено на компьютере

`check_arm.c` запускает реальные байты текущего патча через qemu-aarch64 со штатными
библиотеками из извлечённого rootfs, при двух разных базах отображения PIE.
Использует настоящий машинный код штатного обхода фокуса и callback истечения.
Подменены регистрация/остановка таймера, repaint, запись глобального фокуса и
получение обычного цвета; дисплей и аппаратные устройства не эмулируются.

Проверены отпускание кнопки, прямой/обратный обход и переход через край,
пустой фокус/вектор, компонент вне текущего вектора, другой тип компонента,
другой экран, повторный показ, штатное снятие флага, таймер 2000/500 мс,
янтарный/штатный цвет, вложенный компонент и ограничение поиска предков.
Проверяются неизменность тестовых значений параметров и передача аргументов.

Это проверка машинного кода и взаимодействия с установленными точками вызова.
Она не подтверждает видимость текста на реальном экране, устойчивость реального
аудио или работу таймера в реальном приложении. Полный модифицированный процесс
на компьютере не запускался. В build-info.json статус hardware_tested=false.

## Воспроизводимая сборка

Из каталога проекта в WSL:

```sh
mkdir -p build
aarch64-linux-gnu-gcc -c -o build/peek.o src/peek.S
aarch64-linux-gnu-ld -T src/peek.ld -o build/peek.elf build/peek.o
aarch64-linux-gnu-objcopy -O binary --only-section=.text build/peek.elf build/peek.bin
aarch64-linux-gnu-objcopy -I binary -O elf64-littleaarch64 -B aarch64 build/peek.bin build/peek-data.o
aarch64-linux-gnu-gcc -O2 -Wall -Wextra -Werror -mbranch-protection=standard -Wl,-z,noexecstack src/apply_peek.c build/peek-data.o -o build/apply-peek
```

Затем из Windows-каталога рабочего пространства: `python sd-k-value-peek/build.py`.
Скрипт сборки ничего не записывает на SD. SHA-256 исходного загрузчика сверяется
с отдельно сохранённой физической проверкой. Прошедший физическую проверку ZIP
в `sd-clone-trial/releases` не изменяется.
